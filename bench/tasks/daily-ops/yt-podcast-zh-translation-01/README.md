# yt-podcast-zh-translation-01

## 出处

来自 Rafael 的真实日常工作流：把一期英文播客/访谈视频翻译成中文全文，供个人阅读。真实来源 URL 尚未填入 `task.yaml`——等第一次实际采集/跑分时补上。

## 这是一个新的任务类别：外部内容依赖型任务

与 bench 现有任务（如 `coding/ts-ticker-format-01`）不同，本任务的 fixture 不是一份密封、可离线复现的起始工作区，而是一个外部 URL——agent 需要联网抓取内容才能完成任务。这打破了 `METHODOLOGY.md`「护栏」里"fixture 隔离、一次性、离线可跑"的既有假设，是刻意记录、非默默绕过：

- **可复现性打折扣**：同一个 URL 不同时间跑，抓取结果可能不同（字幕变化、视频下架、限流、地域限制）。跑分记录需要标注跑分时间，不能假设长期可复现。
- **需要联网**，与 pi 实例设计里的出网策略直接相关（`PRODUCT.md`「pi Track」、`TODO.md` P1）——这个任务本身就是"出网白名单要不要放行外部媒体源"这个待定决策的一个真实用例，不是抽象讨论。

## 抓取与翻译为什么没拆成两个任务

拆分能让信号更干净（抓取是工具可靠性问题，翻译是模型能力问题，二者混在一起会分不清分数低是哪一环出的问题）。这次按用户决定保留端到端任务——更贴近真实工作流的完整形态。如果后续发现两个能力的信号经常互相污染（比如常因为抓取失败导致整任务判 0，却掩盖了翻译本身其实很强），再回头拆分为 `retrieve-external-media-transcript` 独立任务。

## 版权处理：留到实际采集时决定

本仓库是 **public** 仓库。完整播客文字稿和完整参考译文**不应该**作为 fixture/oracle 内容长期提交进版本控制。当前 `oracle/rubric.md` 只包含打分维度，不含任何具体节目内容。评分时需要的原文参照，按需在评分那一刻获取，不落库。

第一次实际采集时需要决定：判据材料是完全不落库（每次评分现取原文做参照），还是存一个不越过合理使用边界的极短片段用于说明评分标准。这个决定留到那时候，不在本次框架搭建中预先拍板。
